## Findings (RAN, verbatim from gate JSONs above)

1. **Per-cell Merkle producer is MORE expensive than the direct-sha at the
   production commit point** -- this SHARPENS the r132 optimistic reading.
   a0 (direct-sha) vs a1 (Merkle producer) = 71,981 vs 164,484 g = 2.28x
   in the direct-sha's FAVOR at the production H=10 shape. r132 called
   40,618 vs 69,232 "1.70x for the node" but the 40,618 (r131 np2) probe
   priced only the sponge node and left the per-leaf commitments as
   unconstrained public inputs. The REAL producer-side Merkle route (a1)
   must build the leaf commitments TOO, and that is exactly what the
   164,484 g/cell extra pays for (164,484 - 71,981 = 92,503 g/cell delta).
   The lever therefore does NOT survive on "per-cell nodes cheaper than
   per-cell direct-sha" -- they are the opposite at the per-cell
   granularity. It survives on (a) frequency amortization (attested ONCE
   at C2/C3; consumer C4 would otherwise re-commit on every decryption
   request) and/or (b) swapping the consumer arm to the r132 p3-class
   binding so C4 stops paying 71,981/cell.
   Both elbows are now RAN-anchored:
     producer side (a1)              = 164,484 g/cell (isolated, not amort)
     consumer-removed-C4 current     = 71,981 g/cell (a0 = p4/cell)
     consumer-BOUND-C4 (r132 p3)     = 2,749 g/cell  (binding only, no sponge)

2. **The per-cell (a)-unit is committee-shape-invariant (H not an input).**
   a0 and h14_cell use the IDENTICAL call
   `compute_share_encryption_commitment_from_message::<N, SHARE_ENCRYPTION_\
   BIT_MSG>` over a single `Polynomial<N=8192>` share; both read only the
   ring degree N (= 8192, secure) and the message-bit width from
   `configs::dkg`. The committee shape (H=10 vs H=14) is NOT one of that
   function's type/value inputs, so it cannot move a single share's
   commitment. Hence a0 (H=10) and h14_cell (H=14) are digit-exact at
   71,981 g / 3,644 ACIR -- and the 71,981 g figure is also stable across the
   C3/C6 lib edits (the share-commitment path is untouched by them). All the
   committee-size dependence of the WHOLE (a) block lives in the x30- / x42-
   cell construction, never in the per-cell op.

3. **(a)-block scales by the committee-size ratio, within-lib.** b1 (30-cell
   production (a) block, uniformly-shaped merkle-node spine) measured at H=10,
   THIS round, THIS tree = 2,158,908 g. h14_v0 − h14_v1 (the 42-cell (a) block
   at H=14, same tree) = 3,022,405 g. RATIO = 3,022,405 / 2,158,908 =
   **1.4000** = exactly the cell-count ratio 42 / 30 = 1.4000 (within
   floating-epsilon; same-lib, same-tree, same branch, different H). The
   per-cell unit does NOT grow; the block grows ONLY because the cell count
   grows. (a)'s fraction of V0 rises along with it: H14: 3,022,405 / 4,484,
   154 = **67.40% of V0** (H14 V0); H10 cross-lib r131 V0-shape figure
   2,158,861 / 3,571,446 = 60.45% (H10). This round's within-lib H10 figure
   + H14 figure gives a clean 67.40 % fraction at the NEW production shape.
   Honest note: the C6/C3 commits (circuits/lib/src/core/threshold/
   share_decryption.nr 1fb1ef64 + dkg/share_encryption.nr 39b5de51) PRE-DATE
   both b1 and h14_v0 by several commits; neither touches
   circuits/lib/src/core/dkg/share_decryption.nr (the specific file h14_v0
   reads), so V0 and V1 stay equal-footing; the caveat still applies to
   where 3.57M of the total V0 came from across the H-shape-move-outside-
   the-(a)-block portion of the circuit ((b) fold + (c) floor, N-bound /
   ring-bound).

4. **H14 V0→V1 wall/peak (self-contained, RAN, no across-lib anchor required).**
